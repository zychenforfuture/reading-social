# 架构设计提升计划

## 1. 目标
- 建立清晰的分层架构（Route -> Service -> Repository）
- 降低路由层耦合度，提升可测试性与复用性
- 建立统一错误模型和统一响应规范

## 2. 现状问题
- 路由层承担过多业务逻辑和数据访问逻辑
- 错误处理方式不统一，日志上下文不完整
- 缺少明确的领域边界（文档、评论、通知之间存在交叉逻辑）

## 3. 行动项
- 短期（1-2 周）
  - 定义 API 分层规范与目录约定（service/repository/contracts）
  - 新增统一错误类型（业务错误、参数错误、权限错误、系统错误）
  - 新增统一 API 响应结构（code/message/data/requestId）
- 中期（3-6 周）
  - 将 document、comment、notification 三大模块迁移到 Service 层
  - 将 SQL 查询下沉到 Repository 层，统一事务入口
  - 引入领域事件（如 CommentCreated、DocumentProcessed）用于解耦通知逻辑
- 长期（6-10 周）
  - 为 Worker 与 API 建立事件契约版本化机制
  - 形成架构评审清单并纳入 PR 模板

## 4. 里程碑与验收
- M1：完成架构规范文档与模板代码
- M2：核心三模块完成分层改造
- M3：80% 新需求按新分层落地
- 验收指标：
  - 路由文件平均代码行数下降 30%
  - 业务逻辑单元测试覆盖率显著提升
